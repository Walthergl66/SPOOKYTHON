## Objetivo y alcance

Permitir que una URL pública temporal deje a cualquier visitante usar Reto, Simulador y Jugar como operador, cada uno con un mundo aislado por cookie anónima. El backend conserva un único proceso/coordinador; la multisesión significa varios mundos independientes dentro del mismo proceso, no varias réplicas ni multijugador.

Las sesiones se guardan en memoria, con máximo por instancia, expiración tras tres horas inactivas por defecto y límites adicionales del proxy. La instancia pública actual sobreescribe esos valores con cuatro sesiones y 900 segundos inactivos. Reinicio o despliegue elimina las partidas. No hay cuentas, persistencia, recuperación, escalado horizontal, SLA ni protección absoluta contra abuso automatizado. `/paso` conserva su API key y no se inserta una clave en el frontend.

## Implementación y límites

El adaptador `RegistroSesionesDemoMemoria` guarda SHA-256 del token y asocia cada sesión con un coordinador compuesto; controles/dominio no reciben el token. El control automático y el juego humano usan mundos distintos dentro de la misma cookie; los endpoints de panel y órdenes resuelven servicios desde esa sesión. El contexto humano se crea de forma diferida al entrar a Jugar, y su reloj arranca después de la aparición del jugador. Cambiar a Simulador o Reto detiene el reloj humano para evitar que dos modos compitan dentro de la sesión. Middleware HTTP fija o renueva actividad para `/panel/`, `/demo/`, `/reto/`, `/juego/` y `/paso`; la cookie se emite al crear sesión. El frontend público espera el bootstrap `/demo/sesion` antes de montar el dashboard para evitar solicitudes iniciales sin identidad.

El perfil público se activa solo con `NAVIRA_PUBLIC_DEMO_CONTROL=1`. `NAVIRA_PUBLIC_MAX_SESSIONS` y `NAVIRA_PUBLIC_SESSION_IDLE_SECONDS` acotan recursos. En la implementación temporal vigente, Lightsail ejecuta backend y frontend como contenedores Docker con red host; Nginx del host termina TLS y proxifica a la interfaz en loopback, que enruta al backend. La instancia debe permanecer única porque coordinador y sesiones están en memoria. La URL usa `nip.io`, un nombre temporal de terceros, no un dominio propiedad del proyecto. Las actualizaciones por GitHub Actions y sus requisitos de red están en [ADR-047](../../arquitectura/decisiones/0047-despliegue-lightsail-desde-github-actions.md) e [infraestructura](../../operacion/infraestructura.md). Revisar también [seguridad](../../operacion/seguridad.md) y [costos](../../operacion/costos.md).

CAM-159 añade la configuración para Vercel sirviendo `frontend/` y proxificando rutas del tablero y `/ws/*` al Web Service Render Free definido en `render.yaml`. El backend usa un worker, máximo de una sesión y 900 s de inactividad; la API key se genera en Render. CAM-160 aprovisionó `navira-api-walthergl66-v9ux` y confirmó `/salud` directo HTTP 200, con dominio de producción Vercel `https://navira-two.vercel.app` configurado en `NAVIRA_ALLOWED_ORIGINS` (el redeploy estaba en curso). El frontend visible aún fue construido desde `master` (`febaddcc`) sin rewrites; `frontend/vercel.json` actualizado apunta al hostname Render confirmado y sigue sin desplegar. `frontend/.env.production` define `VITE_PUBLIC_DEMO=1` para hacer el bootstrap de cookie. Falta probar la integración HTTPS proxy.

Render Free puede dormir tras 15 minutos sin tráfico, tener arranque frío aproximado de un minuto, reiniciarse y perder el filesystem; las partidas y sesiones en memoria se pierden en cada reinicio. El cupo único es una precaución por los recursos del plan y todavía falta medir el mapa cargado. No usar esta alternativa para prometer persistencia, multiworker, disponibilidad continua o SLA. Ver [ADR-054](../../arquitectura/decisiones/0054-hosting-vercel-render-free.md), [infraestructura](../../operacion/infraestructura.md) y [costos](../../operacion/costos.md).

## Verificación y estado

T-58 valida aislamiento por cookie, inicio de mundos distintos, origen, capacidad, expiración y limpieza; la prueba ASGI y el smoke HTTPS Lightsail recorren Juego → Reto en un navegador y Simulador en otro, confirman tres `runId` distintos y Origin ajeno 403. La prueba focalizada `test_origen_proxy_solo_admite_dominios_configurados_exactamente` además comprueba un origen Vercel permitido detrás de un Host Render y rechaza un dominio atacante con prefijo coincidente. CAM-159 ejecutó `python -m unittest discover -s tests -p 'test_public_demo.py'` (6/6). `nginx -t`, el health check HTTPS y el estado del panel “En vivo” del navegador pasan para Lightsail. CAM-131 actualizó por SSH administrativo las imágenes al SHA completo registrado y verificó HTTP 200 en `/` y `/salud`. En CAM-160, el Render directo `/salud` responde HTTP 200 y el frontend Vercel está visible, pero este último aún no contiene los rewrites. El proxy HTTP/WebSocket, bootstrap/cookie, mutaciones, reconexión y arranque frío a través de Vercel no están verificados; el redeploy Render por la allowlist estaba en progreso. Tampoco hubo prueba de carga concurrente nueva, revisión visual del mapa en Jugar o lectura actual de recursos/costos AWS. No marcar esta SPEC verificada por builds o pruebas locales solamente.
